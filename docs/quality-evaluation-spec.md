# 품질·평가 명세 — 데이터 전처리 자동화 프로토타입

| 항목 | 내용 |
|---|---|
| 문서 | 사전 문서 5종 중 ④ 품질·평가 명세 |
| 버전·상태 | **v0.2 (2026-11-02) — 확정.** Claude 작성 → Codex 리뷰·토론 합의 24건 → 규민님 결정 4건(10절) |
| 상위 문서 | `docs/prd.md` v0.2(8절 성공 기준), `docs/functional-spec.md` v0.2, `docs/technical-design.md` v0.2, `docs/benchmark.md` |

> 이 문서는 **무엇을 어떻게 재는지**(공식·분모·판정 순서·절차)와 **서비스 안의 판단 기준**(초기값)을 정한다.
> **최종 목표 수치는 여기서 정하지 않는다.** PRD 8절대로 개발셋 사전 측정 뒤, 최종 평가 전에 8절 고정 기록으로 정한다.
> 모든 수치는 합성 벤치마크 기준이며 실제 업무 효과가 아니다.

## 1. 원칙

1. 헤더 매핑·셀 표준화·검토·유지는 따로 집계한다. 서로 다른 단위를 하나의 정확도로 합치지 않는다.
2. 개발 중에는 개발셋·개발 fixture만 쓴다. 최종 평가셋은 개발 완료·조건 고정 후 **한 번**, 결과를 본 뒤 튜닝하지 않는다.
3. 자동 결과와 사람이 확인한 최종 결과를 따로 잰다.
4. review는 "알렸는가(탐지)"와 "원문을 지켰는가(보존)"를 따로 재고, 복원 정확도는 채점하지 않는다.
5. 정답에 없는 파생 경고를 오탐으로 일괄 처리하지 않는다.
6. 10건 미만인 항목은 비율이 아니라 건수로 보고한다.
7. 분모에서 실패·유실을 조용히 빼지 않는다. 분모가 0이면 N/A로 표시한다.

## 2. 벤치마크 현황

**개발셋 (`evaluation_private/development/cases.jsonl`, 4,567건)** — Claude·Codex가 각각 집계해 일치 확인

| 행동 | 유형 | 건수 |
|---|---|---|
| normalize | datetime_format 1,577 · money_format 1,227 · enum_case 1,135 · phone_format 256 · null_token 139 · outer_whitespace 90 | 4,424 |
| map_column | header_alias (한글 헤더) | 106 |
| review | duplicate_pk 12(행 단위 `column="*"`) · required_missing·truncated_phone·ambiguous_missing·ambiguous_date·total_conflict·unknown_fk·zero_quantity 각 1 | 19 |
| keep | 정상 예외 6종 각 3 | 18 |

- 개발셋의 `pattern_group`은 모두 seen이다. review 19건 모두 `expected_value`가 없다.

**평가셋 (2,375건)**
- 행동별 총수는 `evaluation_private/manifest.json`으로 확인된다: normalize 2,232 · map_column 106 · review 19 · keep 18.
- seen/unseen 교차 건수(normalize seen 1,852 / unseen 380, map_column unseen 106, review·keep seen)는 manifest에 없다. **이 건수는 2026-11-02 Claude가 이 문서 v0.1을 쓰며 평가셋 정답 파일(`evaluation_private/evaluation/cases.jsonl`)에서 행동×표현 건수만 집계한 것이다.** 값·사례 내용은 출력하지 않았고, 3절 기준·fixture를 이 건수로 정하지 않았다. 이 접근은 **사전 접근 이력**으로 8절 고정 기록에 남긴다. 이후 평가셋 정답 파일은 최종 평가 전까지 열지 않는다.

**이 현황에서 나오는 제약**
- **매핑:** 평가셋 헤더가 영어 별칭이라는 점은 `docs/benchmark.md`(공개 계약)에 이미 적혀 있다. 영어 별칭 매핑은 `schema.json`·정책 문서만 보고 만든 개발용 별칭 fixture로 사전 측정한다.
- **review·keep:** 유형마다 1~12건이라 건수만 보고한다.
- **정합성:** 금액 합계 모순을 명시적으로 넣은 사례는 `total_conflict` 1건이다. `unknown_fk`·`zero_quantity`·`duplicate_pk`도 관계 검사·계산 가능성에 영향을 준다. 정합성 규칙 전체의 성능을 벤치마크 수치로 주장하지 않고 규칙별 fixture 기능 테스트(T-10)로 검증한다.
- **unseen 표준화:** 현재 고정 개발셋에는 unseen으로 분류된 사례가 없다. 공개 schema·정책 기반의 독립 개발 fixture로 정책 변환 기능을 테스트하지만, 그 성능을 평가셋 unseen 성능으로 대신하지 않는다. `pattern_group=unseen`은 "개발 분할에 없던 표현"이라는 뜻이며 공개 정책에도 없던 표현이라는 보장은 아니다.

## 3. 서비스 안의 판단 기준 (초기값)

모든 값은 **설계 초기 가정**이다(개발 사전 측정 전). 개발셋·개발 fixture로만 조정하며, 바꾸면 출처를 "개발 사전 측정"으로 고친다. 규칙 사전(`aliases.json`·`pii.json`)과 패턴 정규식도 숫자 임계값과 함께 8절 고정 기록에 넣는다. 각 값은 경계값 바로 아래·같음·위 fixture로 테스트한다.

### 3-1. 헤더 정규화와 매핑 확신 등급 (F03)
- **정규화:** 유니코드 NFKC → 소문자 → 앞뒤 공백 제거 → 공백·`_`·`-`·`.`·`/` 제거.
- **원래 헤더 기록:** 정규화 전 원래 헤더는 항상 그대로 기록한다. 정규화하면 같아지는 변경(예: `Order Id` → `order_id`)도 원래 헤더 변경으로 남긴다(3-3).

| 등급 | 조건 | 처리 |
|---|---|---|
| exact | 정규화한 헤더 = 정규화한 논리 컬럼 이름 | 자동 제안 |
| alias | 정규화한 헤더 ∈ 승인된 별칭 사전 | 자동 제안 |
| reuse | 같은 양식의 효력 있는 재사용 매핑 규칙(원래 헤더 → 논리 컬럼)과 일치하고 그 컬럼에 스키마 변경 감지가 없음(2026-11-05 결정 M6-D2) | 자동 제안 |
| similar | difflib ratio ≥ 0.8인 후보가 정확히 하나 | 확인 필요 |
| shape | 값 형태 서명이 논리 컬럼 규칙과 맞는 후보 | 확인 필요 |
| none | 후보 없음 | 미매핑 |

- exact·alias라도 두 원래 컬럼이 같은 논리 컬럼으로 가거나, 정규화 후 두 원래 헤더가 같아지면(정규화 충돌) 모두 확인 필요.
- similar 후보가 둘 이상이면 동률로 보고 확인 필요(자동 선택 없음).
- 별칭 사전 항목마다 근거(스키마 설명·개발용 헤더·정책 문서)를 기록한다. 평가셋 헤더를 근거로 쓰지 않는다.

### 3-2. 테이블 분류 (F03)
- 파일·시트 이름을 정규화해 표준 테이블 이름·별칭과 같으면 자동 제안.
- 아니면 **분모 = 그 표의 원래 헤더 수(빈 머리글 제외)**, 분자 = 그 테이블의 논리 컬럼에 exact·alias로 매칭되는 헤더 수. 1위 비율 ≥ 70%이고 2위와 30%p 이상 차이나면 자동 제안, 아니면 확인 필요. 헤더 0개·동률은 확인 필요.

### 3-3. 스키마 변경 감지 (F10) — 알림 기준(오류 아님)

| 변화 | 알림 조건과 분모 |
|---|---|
| 원래 헤더 변경 | 원래 헤더 문자열 목록이 다르면(정규화 전 기준) |
| 컬럼 추가·삭제 | 정규화 헤더 집합 차이 |
| 이름 변경 의심 | 사라진 컬럼과 새 컬럼의 대표 형태 서명(최빈)이 같고, 비어 있지 않은 값 기준 형태 서명 분포 겹침 ≥ 80%. 양쪽 비어 있지 않은 값이 5개 미만이면 판단 안 함(표본 미달 표시) |
| 값 모양 변화 | 비어 있지 않은 값 기준으로 대표 형태 서명이 바뀌었거나, 이전에 없던 서명의 비율 ≥ 10%. 5개 미만이면 표본 미달 |
| 숫자·날짜 범위 | 원문 값 중 논리 설정 타입으로 파싱되는 값만으로 최소·최대 비교. 파싱 불가 값은 범위에 넣지 않고 건수를 따로 표시 |
| 범주 새 값 | 허용값 규칙이 있는 컬럼에서, 비교 정규화(strip·casefold 설정) 후 이전에 없던 값 |

### 3-4. 개인정보 후보 탐지 (F11)
- 조건(하나라도): ① 논리 컬럼 이름이 `pii.json` 이름 목록에 있음 ② 원래 헤더에 `pii.json` 키워드가 있음 ③ 비어 있지 않은 값이 5개 이상이고 그중 개인정보 패턴과 맞는 비율 ≥ 80%(분모 = 비어 있지 않은 값, 결측 표현 제외) ④ 자유 텍스트 목록에 있음.
- 비어 있지 않은 값이 5개 미만이면 ③은 판단하지 않고 "표본 미달"로 표시(①②④는 적용).

## 4. 데이터 품질 점수 정의 `quality-v1` (F12)

**공통**
- 계산 대상은 마스킹 전 결과 버전(결정 Q10). 정제 전(입력)과 정제 후(결과)를 같은 실행 계획으로 함께 계산한다.
- 각 차원은 실행 계획에서 실행한 규칙만 쓴다. 분모가 0이면 `not_measured`. 실행 안 한 규칙이 있으면 "부분" 표시와 범위를 함께 보여 준다.
- 정제 전후로 분모가 달라질 수 있다(예: 상태값 표준화로 `required_if` 적용 대상이 바뀜, 파싱 가능 범위가 넓어짐). 그래서 **분자·분모·계산 불가 건수를 양쪽 모두** 표시하고, 검사 가능 범위가 바뀐 것만으로 품질이 좋아졌다고 설명하지 않는다.
- 표시: 0~100 정수(내림). **종합 점수는 표시하지 않는다(결정 E1).**

### 4-1. 완전성 — 단위: 고유 셀
- 대상 셀: 실행한 `required` 규칙의 셀, 그리고 `required_if` 조건이 참으로 판정된 셀. 같은 셀에 둘 다 걸려도 한 번.
- `required_if` 조건 컬럼을 판정할 수 없으면(조건 값 파싱 불가·결측) 그 셀은 "필수 아님"으로 보지 않고 **계산 불가**로 따로 센다.
- 빈 값 판정: 빈 문자열, 공백만 있는 값, 그 컬럼에 승인된 결측 표현(`missing_values`).
- 분자 = 대상 셀 중 빈 값이 아닌 셀, 분모 = 대상 셀.

### 4-2. 유효성 — 단위: 고유 셀
- 대상 셀: 타입·패턴·허용값·범위 규칙이 실행된 셀 중 빈 값이 아닌 셀. 선택 항목의 결측은 대상이 아니다(위반 아님).
- 같은 셀에 진단이 여러 개여도 한 번. 그 셀에 위반·사람 검토·**남은 표준화 후보**(형식 불일치)가 하나라도 있으면 통과 아님.
- 분자 = 통과 셀, 분모 = 대상 셀.

### 4-3. 일관성 — 단위: 고유 기준 행
- 기준 행 키 = (표준 테이블, 원본 행 식별자).
- 한 행에 적용 가능한 검사 = 그 행이 자식으로서 받는 참조 검사 + 그 행이 기준(anchor)인 정합성 규칙.
- **분모:** 적용 가능한 검사 중 하나 이상이 실제로 판정(`ok` 또는 `violation`/참조 통과·실패)된 행. 한 행은 한 번만.
- **분자:** 판정된 검사 중 위반이 하나도 없는 행.
- 일부 검사가 계산 불가인 행은 판정된 검사로만 통과 여부를 정하되, 그 행 수를 "부분 판정 행"으로 따로 표시한다.
- 모든 검사가 `not_applicable`·`not_computable`인 행은 분모에서 빼고 건수를 따로 표시한다.

### 4-4. 유일성 — 단위: 고유 행
- 대상 행: 유일성 검사(PK·다른 unique 키·동일 행 중복)가 하나 이상 실행된 테이블의 행.
- 키 중복 그룹이나 동일 행 중복 그룹에 **속한 모든 행**(초과분만이 아님)은 미통과. 여러 그룹에 겹쳐도 한 번만.
- 키 값이 비어 있어 유일성 비교를 할 수 없는 행은 계산 불가로 분모에서 빼고 따로 센다.
- 어떤 유일성 검사가 실행됐는지(PK·unique 키 목록·동일 행) 범위를 표시한다.

### 4-5. 손계산 fixture (단위 테스트)
한 행에 위반 여러 개 · 중복 그룹 중첩 · 정상 선택 결측 · 조건부 필수 적용이 정제 전후로 바뀜 · 일부 검사 불가 · 전체 분모 0 — 각각 손으로 계산한 분자·분모·계산 불가 건수와 일치.

## 5. 채점 명세 (F14)

### 5-1. 입력
- **원본 비교 기준:** 고정된 실제 오염 입력(`data/dirty/<split>/`). baseline은 오염 전 데이터라 입력값으로 쓰지 않고, row-lineage와 함께 전체 대응·무변경 확인의 보조 근거로 쓴다.
- **평가용 입력 등록표:** 정답의 `input_file` ↔ 실제 업로드 항목 ID(이름이 같은 파일도 구분). 최종 평가 시 업로드와 함께 만든다.
- **서비스 산출물:** 매핑 버전(자동 제안 — 사람 확인 전 동결본, 최종), 결과 CSV, `changes.json`, `after.json`, `integrity.json`, `held.json`, 역추적 표, 실행 상태.
- 채점기만 정답을 읽는다(TD 11절).

### 5-2. 위치 맞추기
- **헤더 사례**(`record_number=0`): 매핑 기록에서 채점한다. 데이터 행으로 접근하지 않는다.
- **행 단위 사례**(`column="*"`): 셀이 아니라 행. 그 원본 행(입력 파일·레코드 번호)이 중복 그룹에 들어갔는지(탐지)와 결과에 그대로 남았는지(보존)를 각각 판정한다.
- **PK가 같은 행:** clean_pk로 맞추지 않는다. 원본 행 위치로만 맞추며, 원본 행과 중복 추가 행은 서로 다른 행이다.
- **행 순서·통합:** 서비스 역추적 표로 원본(업로드 항목·시트·레코드·컬럼)에 연결한다.
- **분모에서 빼지 않는 것:** 매핑 오류, 제외 컬럼, 발행 제외 테이블, 결과 누락, 행 삭제, 예상 밖 행 추가 — 모두 실패 범주로 보고한다.

### 5-3. 행동별 판정

**normalize** — 위에서부터 첫 번째로 맞는 범주 하나만. 범주 합계 = n.

| 순서 | 범주 | 조건 |
|---|---|---|
| 1 | 유실 | 결과 행·컬럼·산출물이 없음(발행 실패 포함) |
| 2 | 정답 | 결과 CSV 값이 `expected_value`와 정확히 같은 문자열(`""`는 빈 필드. 문자열 `null`·`None`·공백과 다름) |
| 3 | 오변환 | 원문과도 정답과도 다른 값(보류 목록에 있어도 오변환) |
| 4 | 보류 | 원문 그대로이고, `held.json` 또는 같은 셀의 위반·검토 등 실제 보류 근거가 있음 |
| 5 | 누락 | 원문 그대로이고 보류 근거가 없음 |

- 정답이어도 `changes.json`에 승인된 변경 기록이 없으면 0건 조건 위반(5-4)으로 따로 센다. 논리 null은 `changes.json`의 `logical_after`로 추가 확인한다.

**map_column**

| 구분 | 판정 |
|---|---|
| 자동 | 사람 확인 전 동결본 기준: 정답 / 오답 / 확인 필요(충돌) / 후보 없음 |
| 최종 | 정답 / 오답 / 미완료(사용자가 빼거나 끝내지 않음 — 분모에 남김) |
| 지표 | 자동 정확도 = 정답 ÷ 자동 제안(자동 제안 0건이면 N/A), 자동 범위 = 자동 제안 ÷ 전체, 최종 정확도 = 정답 ÷ 전체 |

**review** — 탐지와 보존을 따로 판정(건수 보고).

| issue_type | 탐지로 인정하는 근거 |
|---|---|
| duplicate_pk (행 단위) | 그 원본 행이 해당 PK의 키 중복 그룹에 포함됨 |
| required_missing | 그 셀의 `required` 위반 |
| truncated_phone | 그 셀의 패턴·형식 관련 사람 검토 |
| ambiguous_date | 그 셀의 타입·형식 관련 사람 검토 |
| ambiguous_missing | 그 셀의 결측 의미 관련 사람 검토 |
| unknown_fk | 그 셀의 참조 위반 |
| zero_quantity | 그 셀의 범위 위반 또는 사람 검토 |
| total_conflict | 그 주문을 기준 행으로 하는 R02 위반 묶음(같은 주문의 다른 규칙 위반은 인정 안 함) |

- 같은 위치의 다른 종류 경고는 탐지로 인정하지 않는다.
- 보존: 셀 사례는 결과 값 = `observed_value`, 행 사례는 그 원본 행이 결과에 그대로 남음(삭제·병합 없음).
- 복원 정답을 만들거나 `clean_value`로 복원 정확도를 채점하지 않는다.

**keep** — 네 가지를 구분하고 앞의 둘만 오판으로 센다.

| 구분 | 조건 |
|---|---|
| 값 변경 | 결과 값 ≠ 입력 값 → 오판 |
| 오류 확정 | 업무 규칙 위반 분류, 또는 그 값을 바꾸는 표준화 후보 제안 → 오판 |
| 추가 검토 요청 | 사람 검토 분류 → 오판 아님, 건수 따로 보고 |
| 참고 관측 | 정상 관측·정보성 표시 → 오판 아님 |

### 5-4. 불필요 변경과 0건 조건

**불필요 변경 네 범주** (겹치지 않게, 합계·분모 있는 오수정률로 보고. 헤더 매핑은 별도)

| 범주 | 분모 |
|---|---|
| normalize 대상의 오변환 | normalize 사례 수 |
| review 보호 대상의 변경·행 삭제·병합 | review 사례 수 |
| keep 대상의 변경 | keep 사례 수 |
| 그 밖에 유지해야 할 셀의 변경 | 정답 사례가 아닌 모든 셀 수(행 단위 사례의 행도 셀 단위로 대조, 같은 셀에 normalize 정답이 있으면 그 정답이 우선) |

**0건 조건 두 축을 구분한다**

| 조건 | 확인 자료 |
|---|---|
| 승인 없는 변경 0 | 서비스 감사 기록(`changes.json`·적용 계획)과 결과 대조 |
| 정답 기준 비대상 오수정 0 | 채점기(위 넷째 범주) |

잘못된 변경을 사용자가 승인하면 앞의 조건은 통과해도 뒤의 조건은 실패한다.

### 5-5. 보고서 형식
- 표: 행동 × `pattern_group` × `issue_type` 별 n과 범주별 건수. 행동끼리 합친 총 정확도는 만들지 않는다.
- 비대상 셀에 붙은 경고는 건수만 기술하고 오탐으로 판정하지 않는다.
- 머리말: 코드 커밋, 채점기·판정 규칙 버전, 설정 스냅샷 해시, 평가 조건, 실행 시각, 재시도 사유, "합성 벤치마크" 문구.
- 재현성 비교는 표 내용만(시각 등 메타데이터 제외).

## 6. 효과 측정

### 6-1. 규칙 재사용의 검토 감소 (F09)
- **나누기:** 테스트 도구가 개발셋 입력을 같은 템플릿의 두 묶음 A·B로 나눈다. 고객 단위로 나눠 주문·결제·출고·반품·환불과 중복 행의 참여 관계를 함께 옮기고, 상품·SKU·카테고리 기준표는 양쪽이 공유한다. 서비스는 나누기용 정답을 읽지 않는다. 평가셋은 쓰지 않는다.
- **상태 통제:** A를 실행해 재사용 규칙을 승인한 **직후의 앱 상태(DB·workspace)를 복제**해 두 조건의 시작점으로 쓴다. 코드·설정·B 바이트·출처/양식·실행 대상·검사 범위를 같게 고정한다. 차이는 재사용 규칙으로 미리 선택했는지 하나뿐이다. B①이 B②의 프로파일·별칭·승인·캐시를 바꾸지 않는다.
- **같은 최종 결정:** 두 조건 모두 같은 최종 적용 결정을 확인한다(한쪽에만 다른 정보를 주지 않음).
- **감소율** = (① 검토 항목 − ② 검토 항목) ÷ ① 검토 항목. ①이 0이면 N/A.
- **검토 항목(화면 판단 항목 지표):** 확인 필요 매핑 수 + 미리 선택되지 않은 표준화 묶음 수(2026-11-05 결정 M6-D4: 재사용 규칙으로 덮이지 않은 묶음 — 규칙이 없는 양식의 기본 전체 선택은 미리 선택으로 세지 않는다)(묶음 안 일부만 미리 선택된 경우도 1로 셈) + 사람 검토 고유 셀 수 + 업무 위반 그룹 수(중복 그룹·정합성 위반 묶음은 그룹 단위) + 보류 셀 수. 서로 다른 단위를 더한 지표이며 작업 시간 감소와 같다고 보지 않는다. 합계와 구성 항목을 함께 보고한다.
- **안전 비교:** ①·②의 normalize 범주, review 탐지·보존, keep 오판, 불필요 변경이 같거나 나아야 한다. 검토가 줄었는데 탐지·보존이 줄면 효과로 주장하지 않는다.

### 6-2. 처리 시간
- 엔진 시간: 서버 처리 시간(3-5 측정 방식).
- 사람 포함 시간: 최종 평가에서 규민님이 화면으로 진행할 때 단계별 시작·끝(E2). 이 사용자·절차의 관측치로만 보고하고, 수작업과 비교하거나 일반화하지 않는다.

### 6-3. AI 제안 비교 (조건부 — AI 구현 재확인 후)
- 같은 입력·같은 초기 상태에서 AI 끔/켬을 실행하고 5절 지표·검토 항목·처리 시간을 비교한다. 모델·프롬프트는 최종 평가 전 고정.
- 같은 사람이 반복하며 익숙해지므로, 사람 포함 시간 차이를 AI 효과로 주장하지 않는다.

## 7. 최종 평가 절차

1. **개발 완료:** 모든 P0·P1 기능(재확인된 경우 AI 포함)이 개발셋·fixture 테스트를 통과.
2. **사전 측정:** 개발셋·개발 fixture로 5절 지표와 3-5 응답 시간을 측정.
3. **고정 기록 작성·커밋(8절).**
4. **최종 실행:** `--split evaluation --confirm-final`로 조건마다 한 번.
   - 매핑 확인은 규민님이 화면의 입력·근거만 보고 한다(정답 비공개, 결정 E2). 자동 제안은 사람 확인 전에 동결해 저장한다.
   - 조건별 실행에 앞 조건의 채점 결과를 쓰지 않는다. **모든 조건의 산출물을 확보한 뒤에 채점 결과를 연다.**
   - 사람의 매핑 수정은 정해진 사용 흐름이며, 결과를 보고 코드·별칭·규칙을 고치는 튜닝과 구분한다.
5. **실패 처리:** 발행이 실패한 조건을 빼거나 정상 셀만 채점하지 않는다. 실패 자체를 보고하고, 진단·변환 성능 중 측정 가능한 범위를 따로 표시한다. 기술적 실패 재시도는 인정 조건(8절)에 맞을 때만 하고, 그때까지 본 산출물·점수를 기록한다. 점수를 본 뒤 고친 실행은 기술 재시도가 아니다.
6. **보고:** 결과를 목표와 함께 그대로 보고한다. 결과를 본 뒤 조건을 바꾸면 그 뒤 버전은 "미사용 평가"로 부르지 않는다.

**주장 문장 원칙:** "합성 벤치마크(가상 쇼핑몰, 새 고객·거래·입력 표현)에서 …"로 시작하고, 실제 업무 효과·일반화로 표현하지 않는다.
