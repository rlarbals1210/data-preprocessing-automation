## 1. 원칙

1. **세로로 먼저 끝까지:** P0 사용자 흐름만으로 S1(처음 받은 파일 정리)을 웹에서 끝까지 완료하는 것을 첫 목표로 한다. P1 기능은 그 위에 하나씩 얹는다.
2. **작게 만들고 바로 검증:** 한 작업은 리뷰 한 번에 읽을 수 있는 크기로 나눈다. 변경 400줄(테스트 제외)은 강제 제한이 아니라, 응집성과 실패 경로를 함께 검토할 수 있는지 판단하는 가이드다.
3. **기존 동작 보존:** 엔진 확장은 추가만 한다. 명령줄 회귀(T-01)가 생긴 뒤에는 매 Python 작업마다 돌린다.
4. **정답을 보지 않고 만든다:** 개발 중 접근 범위는 8절을 따른다.
5. **기록이 끝나야 작업이 끝난다:** 검증 통과 + 리뷰 반영 + 기록 + 커밋까지가 한 작업이다.
6. **가짜 완료 금지:** 가짜 구현이나 단순 skip으로 테스트를 통과시켜 완료로 세지 않는다. 미구현 기능을 정상 결과로 대체하지 않는다.

### 2-1. M4~M7의 의존

기본 순서는 M4 → M5 → M6 → M7이다.

- M4(F05)는 M1의 실행 계획·표준화 뷰·적용 계획·발행 검증 훅에 연결한다.
- M5(F08)는 M1에서 이미 만든 `result_version`·스냅샷·감사 기록을 사용한다. 결과 버전의 기반 자체를 M5까지 미루지 않는다.
- M6(F09·F10)는 과거 업로드 실행·템플릿·설정/승인 버전·기준 프로파일이 필요하다.
- M7(F12)은 F04뿐 아니라 M4의 F05 결과·검사 범위를 사용한다.
- M7(F13)은 F11의 마스킹 공유 모델과 F12 점수를 사용한다.
- M7의 출처별 품질 추이는 비교 기준과 과거 실행 기록이 준비되어야 검증할 수 있다.

M4~M7의 순서는 위 의존을 만족할 때만 조정하고, 조정하면 규민님 확인 후 이 표에 기록한다. 순서를 조정해도 미구현 기능을 정상 결과로 대체하거나 해당 E2E를 완료 처리하지 않는다.

## 4. 작업 흐름 (한 작업의 순서)

기본은 **Claude 구현 → Codex 리뷰**다. 규민님이 요청하면 역할을 바꾼다(그때도 같은 순서).

1. **시작 확인:** AI-brain 변경 사항 확인, 코드 저장소 `git status` 확인(다른 작업의 변경을 포함하거나 버리지 않음), 이 문서에서 작업 ID 확인.
2. **브랜치(G1):** 작업 브랜치를 만들지 않고 `main` 하나에서 작업한다. 테스트가 통과하는 상태로만 커밋한다.
3. **구현:** 테스트를 먼저 또는 함께 쓴다. 관련 AC·T 번호를 테스트 이름이나 docstring에 적는다.
4. **자체 확인:** 5절 완료 기준을 직접 돌려 본다.
5. **리뷰 요청(G2):** Claude가 6절 체크리스트로 먼저 자체 검토한다. 문제나 쟁점이 없으면 Codex 리뷰 없이 진행하고, 자체 검토 결과를 기록에 남긴다. 판단이 갈리는 설계·계약·격리 쟁점이 있을 때만 규민님이 Codex에 바로 붙여 넣을 프롬프트를 만든다(꼭 필요한 내용만: 작업 ID, 쟁점, 근거, 관련 AC·T, 변경 파일·테스트 결과 중 쟁점에 필요한 것).
6. **리뷰 반영:** Codex 지적을 코드로 확인한 뒤 반영하거나, 반영하지 않을 이유를 답 프롬프트로 보낸다. 더 나눌 의견이 없을 때만 "토론 끝"으로 마친다.
7. **반영:** `main`에 바로 커밋한다. Codex 리뷰를 거친 작업은 지적 반영 커밋을 같은 `main`에 이어서 남긴다.
8. **기록:** 10절에 따라 기록하고 커밋한다. 코드 저장소 푸시는 규민님 Mac에서 한다.

**마일스톤 통합 리뷰(G2):** Claude가 마일스톤 끝에 기능 연결·누적 회귀·미완료 AC·다음 단계 의존을 자체 점검하고, 쟁점이 있을 때만 Codex에 묻는다.

**결정 권한:**
- 내부 함수·화면에 드러나지 않는 저장 세부는 Claude·Codex 구현 합의로 바꿀 수 있다.
- 승인·출력·데이터 의미·평가 판정을 바꾸는 계약 변경, 범위·기능·사용자 흐름 변경은 규민님 승인 후 반영한다.
- 단순히 "API·DB 변경"이라는 이유만으로 승인 필요 여부를 일괄 정하지 않는다.

## 5. 완료 기준 (Definition of Done)

모든 작업은 **공통 조건**을 충족하고, **변경 유형별 항목**은 통과 또는 비적용 사유를 기록한다. 아직 구현되지 않은 검증은 통과로 처리하지 않고, 해당 마일스톤의 후속 작업 ID로 추적한다.

### 5-1. 공통 조건
- [ ] 이 작업 ID의 범위 밖 변경이 섞이지 않았다.
- [ ] 개발 단계에서는 평가 입력·정답을 열지 않았다. 최종 평가 작업은 ④ 7~8절에서 승인한 접근·피드백 차단 절차를 지켰다(8절).

## 7. Git·커밋 규칙

- **저장소:** `~/Developer/data-preprocessing-automation`. M0-1의 로컬 `git init`은 승인된 구현 작업으로 Claude가 한다. GitHub 비공개 저장소 생성·원격 연결·코드 저장소 푸시는 규민님이 한다(Claude 쪽에는 GitHub 인증이 없음).
- **작성자:** 실제 author·committer는 규민님 Git 계정. 작성자·커미터를 Claude로 하지 않고, `Co-Authored-By`·세션 링크 같은 AI 트레일러를 붙이지 않는다. 작업 로그의 실제 작업 도구 표기는 AI-brain 공통 규칙대로 남긴다.
- **메시지:** 한국어, `<작업 ID> <무엇을>` 한 줄 + 필요하면 본문. 예: `M1-5 컬럼 매핑 확신 등급과 충돌 처리`.
- **커밋 단위:** 테스트가 통과하는 상태로만 커밋한다. 작업 브랜치 안에서는 여러 커밋을 허용한다.
- **커밋 확인:** 의도한 파일만 스테이징하고 전체 staged 범위를 확인한다. 커밋 후 실제 author·committer, 포함 파일, 메시지를 확인한다. 다른 작업의 변경을 포함하거나 버리지 않는다.
- **차단 경로(Git 제외 + 훅 + CI):**
  - `evaluation_private/`
  - `deliverables/evaluation-answers.zip`
  - `data/clean/` (G4a)
  - `data/dirty/evaluation/`, `deliverables/service-inputs.zip` (G4b)
  - 사례별 오류 상세가 담길 수 있는 데이터셋 검증 보고서(8절 5)
- **경로 검사 훅:** staged/index의 파일 이름만 본다. 새 파일·rename을 포함하고, 차단 경로를 제거하는 staged 삭제는 허용한다. NUL 구분으로 공백·한글 경로를 처리한다. 데이터 내용을 읽거나 저장소 전체를 재귀 검색하지 않으며, 코드·문서 안의 "evaluation" 문자열은 막지 않는다. 훅 파일은 버전 관리하고 clone마다 설치하는 방법을 README에 적는다. 로컬 훅만으로 유출 방지를 보장하지 않으므로 CI에서도 같은 경로 검사를 돌린다.
- **대용량:** 큰 원천·실데이터·실행 산출물은 SSD `대용량-데이터/`. Git에 넣지 않는다.
- **범위:** 이 절은 코드 저장소 규칙이다. AI-brain의 기록·푸시 규칙은 바꾸지 않는다.

## 8. 평가 격리 작업 규칙 (개발자 쪽)

서비스 코드의 격리는 ③ 11절이 정한다. 여기서는 **개발하는 사람(Claude·Codex·규민님)** 이 지킬 규칙을 정한다.

1. **개발 중 접근 가능한 것:** 개발 입력·개발 fixture, 그리고 채점기 개발·검증과 개발 사전 측정을 위한 `development` 정답. 서비스·AI 제안 모델에는 개발 정답도 제공하지 않는다. 작업별로 접근할 입력 범위를 먼저 명시하고 시작한다.
2. **최종 평가 전 접근 금지:** `evaluation_private/evaluation/`과 그 밖의 평가 분할 자료, `deliverables/evaluation-answers.zip`, `data/dirty/evaluation/`, `deliverables/service-inputs.zip`(평가 입력 포함), `data/clean/`(평가 분할의 오염 전 값 포함, G4a). `data/clean/`은 채점기·검증 도구의 승인된 보조 근거로만 쓴다.
3. **M10 단계별 접근:**
   - 고정 전: 평가 입력·정답 내용을 열지 않는다. 필요한 해시는 내용 출력 없이 승인된 절차로 계산한다.
   - 고정 후: 규민님과 서비스가 평가 입력으로 정해진 흐름을 수행한다.
   - 채점기는 정답을 읽되, 사람은 모든 조건의 산출물을 확보한 뒤 점수를 확인한다.
   - 개발 도구가 평가 정답 내용을 해석해 코드·별칭·fixture를 보완하지 않는다.
   - 접근 사고·재시도는 ④ 8절 고정 기록에 남긴다.
4. **AI 도구에 넘기지 않음:** 2의 경로 내용을 Codex·AI 제안 모델 입력·리뷰 프롬프트에 넣지 않는다.
5. **데이터셋 검증 보고서:** `reports/dirty-validation.json` 전체를 집계 전용 파일로 보지 않는다(실패 시 `errors`에 사례 ID·원본 위치·컬럼이 들어갈 수 있음). 열람·Git 허용 대상은 미리 정한 집계 필드(분할별 `input_rows`·`cases`·`actions`·`changed_cells_excluding_duplicate_rows`·`unseen_cases`)로 제한한다. 보고서 전체를 허용하려면 `errors`가 비어 있는지 등 공개 가능 조건을 승인된 절차로 확인한다. 사례별 오류 상세가 담긴 보고서는 제외한다. 허용 집계도 기준·fixture·임계값 조정에 쓰지 않는다.
6. **평가 입력 보존(G4b):** 평가 입력과 ZIP은 로컬에 보존한다. 해시는 별도 보존·동결 기록(④ 8절)에서 관리하고, 파일 경로·해시만 확인하는 승인된 절차를 쓴다. `data/manifest.json`은 정상 기준 13개 테이블의 해시 목록이며 평가 입력·ZIP의 해시 목록이 아니다.
7. **이미 있었던 접근:** 2026-11-02 Claude가 평가셋 정답에서 행동×표현 건수만 집계한 일은 ④ 8절 사전 접근 이력에 있다. 새로 접근이 생기면 즉시 규민님께 알리고 같은 곳에 추가한다.
8. **백업:** 정답 원본이 바뀌는 일이 생기면 SSD `평가정답-백업/<날짜>/`에 새 사본과 `SHA256SUMS`를 만든다.
9. **보장 범위:** 생성기(`scripts/build.mjs`)와 seed로 정상 기준을 다시 만들 수 있다. 따라서 비공개만으로 미노출이 보장되지 않으며, 재생성·열람 금지 작업 규칙을 함께 적용한다. 엄격한 블라인드 벤치마크라고 주장하지 않는다. 이 점을 README와 고정 기록에 그대로 적는다.
