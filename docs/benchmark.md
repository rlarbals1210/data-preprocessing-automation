# 오염 데이터와 평가 정답 v1

여러 담당자가 제각각 작성한 CSV를 정리하는 서비스를 개발하기 위한 합성 벤치마크다. 실제 쇼핑몰 데이터나 서비스 성능 측정 결과가 아니다.

## 무엇을 어디에 넣는가

| 경로 | 용도 |
|---|---|
| `data/dirty/development/` | 개발하면서 반복 사용할 13개 입력 CSV |
| `data/dirty/evaluation/` | 규칙·프롬프트를 고정한 뒤 평가할 13개 입력 CSV |
| `config/normalization-policy.json` | 서비스에 제공 가능한 정규화 정책. 적용 전 사용자 승인 필요 |
| `schema.json` | 서비스에 제공 가능한 목표 스키마 |
| `evaluation_private/<split>/cases.jsonl` | 문제·정상 대조군·컬럼 매핑의 정답 |
| `evaluation_private/<split>/row-lineage.jsonl` | 입력 행과 원본 PK 연결 |
| `evaluation_private/<split>/baseline.json` | 분할별 오염 전 원본, 검증/채점 전용 |
| `evaluation_private/manifest.json` | seed·분할·유형별 집계·원본 해시 |
| `evaluation_private/input-manifest.json` | 입력 파일 행 수·해시 |
| `reports/dirty-validation.json` | 데이터와 정답의 대응 검증 결과 |

서비스에는 dirty 폴더와 목표 스키마·정책만 제공한다. clean, evaluation_private, 생성기, 검증 보고서는 서비스의 파일 탐색·검색·프롬프트에 포함하지 않는다. 폴더를 나눈 것만으로 접근 통제가 생기는 것은 아니다. 추후 서비스 테스트에서는 입력 전용 디렉터리를 마운트해야 한다. 개발용 정답은 규칙 개발에 활용할 수 있으나 평가용 정답으로 튜닝한 뒤에는 같은 파일을 미사용 평가셋이라고 주장할 수 없다.

`deliverables/service-inputs.zip`은 dirty CSV 26개·목표 스키마·공개 정책만 포함한다. `deliverables/evaluation-answers.zip`은 정답·원본 연결·검증 근거를 담는다. 두 ZIP의 사용자를 구분한다. ZIP은 생성 당시 스냅샷이며 데이터를 다시 생성한 후에는 다시 묶어야 한다.

## 분할과 입력 습관

seed 20261016. 고객 ID의 SHA-256 기반 약 70:30 분할 후 주문·결제·출고·반품·환불을 고객과 함께 옮긴다. 거래·고객·저장 배송지 PK는 두 분할 간 겹치지 않는다. 상품·SKU·카테고리 기준표는 공통으로 사용한다. 따라서 새 고객/거래와 새 입력 표현에 대한 평가이며 새로운 상품 카탈로그에 대한 일반화 평가는 아니다.

개발용은 담당자 A/B/C, 평가용은 A/B/C/D의 행을 혼합한다. 실제 이력을 추정한 것이 아니라 생성용 프로필이다. 프로필명은 정답 쪽에만 저장한다.

| 유형 | A/B/C | 평가에 추가한 D |
|---|---|---|
| 전화 | 숫자만, 공백, 괄호 | +82 국가코드 |
| 금액 | 쉼표, 원, 쉼표+원 | ₩ 기호 |
| 날짜 | 공백, 슬래시; 시간대 명시 | 점 구분; 시간대 명시 |
| 결측 | NULL, 없음, N/A | 바깥 공백이 있는 NULL |

개발용은 한글 컬럼명, 평가용은 영어 별칭과 다른 컬럼 순서를 사용한다. 행 순서도 섞는다. 각 후보 셀은 24% 확률로 표기 변형을 검토하되 적용 가능한 유형에만 바꾼다. 따라서 24%가 실제 전체 셀 오염률은 아니다. 검토 사례와 정상 대조군은 별도로 먼저 배치한다. 실제 집계는 manifest를 따른다.

## 정답의 의미

JSONL은 한 줄에 JSON 객체 한 개다. `record_number`는 헤더를 제외한 CSV 레코드의 1부터 시작하는 순번이다. 줄바꿈을 포함한 CSV 필드가 생기더라도 물리적 텍스트 줄 번호와 혼동하지 않는다. 0은 헤더, `column="*"`는 행 단위 중복 사례다. 행 순서가 바뀌면 원본 위치를 추적한 뒤 비교해야 한다.

| expected_action | 채점 기준 |
|---|---|
| map_column | 원본 컬럼을 expected_value의 표준 컬럼에 일대일 연결 |
| normalize | 승인된 정책으로 expected_value에 맞게 정리하고 원문·적용 규칙을 보존 |
| review | 문제를 알리고 원문을 보존. 자동 덮어쓰기·행 삭제·합치기 금지 |
| keep | 값 유지. 정상값을 오류로 확정하거나 임의 수정하면 오수정 |

`observed_value`는 입력 그대로, `clean_value`는 생성 당시 원값이다. **review에는 expected_value가 없다.** 원값을 알고 있다는 이유로 손실된 전화번호나 잘못된 수량을 복구하도록 채점하지 않는다. normalize에서 `expected_value=""`는 빈 CSV 필드(null)를 뜻한다. review에 값이 없는 것과 구분한다.

바꾼 모든 셀과 헤더는 정답으로 추적한다. 중복 PK는 양쪽 행을 모두 review로 지정한다. 명시된 keep 사례 외의 바꾸지 않은 셀도 원칙적으로 유지 대상이며 baseline과 row-lineage로 전체 오수정을 검사할 수 있다. keep의 이상치는 통계적 참고 표시까지 금지하는 것이 아니라 오류 확정·자동 변경을 금지하는 뜻이다.

`pattern_group`은 해당 변형 자체가 개발용에 있는지 구분한다. D 행이어도 대문자 범주처럼 기존 변형이면 seen이다. 헤더 매핑과 셀 정규화는 별도 집계하고, 서로 다른 집계 단위를 하나의 정확도로 합치지 않는다.

## 평가에서 주의할 한계

- cases는 주입 위치와 정상 대조군의 처리 정답이다. 수량 하나가 틀리면 합계·배송 수량 등 여러 검증 규칙이 함께 실패할 수 있다. 그 파생 진단 전체를 나열한 정답이 아니므로 목록에 없는 경고를 모두 오탐으로 채점하면 안 된다. 문제 탐지 정밀도 평가에는 후속 진단 규칙별 정답 정의가 필요하다.
- 검토 사례는 유형당 소수이며 대량 표기 정리와 합쳐 정확도를 부풀리지 않는다. 유형·행동·신규 표현별로 따로 집계한다. 평가용을 확인하며 튜닝했다면 별도 seed/새 패턴 평가셋을 새로 만든다.
- 삭제된 행 복원, 인코딩 깨짐, 따옴표 파손, 중복 헤더, 임의 자연어 구조화는 이번 v1에 포함하지 않는다. 관측 근거가 없는 삭제 행을 복원하라고 요구하지 않는다.
- 합성 분포와 단순한 컬럼 별칭은 실제 현업 난이도를 대표하지 않는다. 정상 데이터와 생성기가 이미 공개된 개발 환경에서는 엄격한 비공개 벤치마크라고 주장하지 않는다.

## 재생성과 검증

프로젝트 루트에서 실행한다. 기존 dirty·정답을 덮어쓰므로 수동 수정본은 별도 보관한다. clean은 변경하지 않는다. Node 환경은 runtime.md를 따른다.

```sh
NODE_BINARY=/Users/gimgyumin/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node SKIP_PREVIEWS=1 python3 scripts/build_dirty.py .
python3 scripts/validate_dirty.py . .
python3 scripts/test_dirty.py . .
```

별도 출력 폴더로 재현 비교하려면 `build_dirty.py . /tmp/moa-dirty-check`처럼 두 번째 인자를 지정한다. 검증은 원본 불변, 분할 전 참조 관계, 거래 PK 분리, 모든 변형의 정답 연결, 정상 대조군, 중복 양쪽 보류, 독립 정규화 계산, 입력 허용 파일만 존재하는지를 검사한다. 고의 정답 누락·값 변조·review 복원값 추가·입력 폴더 정답 유출을 넣은 검증기 테스트도 수행한다.
