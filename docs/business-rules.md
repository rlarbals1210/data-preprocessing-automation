# 모아마켓 업무 규칙 v1

이 규칙은 가상 쇼핑몰의 테스트 정책이다. 실제 기업의 업무 정책이나 관측 통계가 아니다.

## 파일·타입

- 스키마 정본은 `../schema.json`, 데이터 사전은 스키마에서 파생한다.
- CSV: UTF-8, BOM 없음, 쉼표, LF, 첫 행 영문 컬럼명. null은 빈 필드 하나로 표현한다.
- 모든 ID·전화·우편번호·운송장·바코드는 문자열. 바코드는 가상 식별자이며 GS1 체크섬 유효성을 주장하지 않는다.
- 시간은 ISO 8601 `+09:00`. 주문 기간은 2026-07-01~09-30, 스냅샷은 2026-10-15 00:00 KST다. 고객·상품 생성은 주문보다 앞선 6월이다.
- 금액은 KRW 정수. 수량·기재된 무게는 양의 정수. 0원 할인·배송비는 정상이다.
- 빈 고객 전화와 이메일, 상세 주소, 상품 설명·무게·바코드, 배송 메모는 허용한다. 의미가 다른 unknown과 false를 합치지 않는다.

## 거래 관계

1. 모든 기본키는 필수·유일, 비어 있지 않은 외래키는 존재해야 한다.
2. 카테고리는 최대 2단계. 최상위 parent_category_id는 null이며 자기 참조·순환은 금지한다.
3. 고객별 기본 배송지는 최대 1개. 상품은 SKU를 하나 이상 가진다.
4. 주문은 주문 상세를 하나 이상 가진다. `line_total = quantity × unit_price − discount_amount`. 주문금액은 항목 금액 합계+배송비다.
5. 합성 정책: 상품 소계 50,000원 이상이면 배송비 0원, 미만이면 3,000원. 항목 할인은 개당 500원 또는 0원으로 배분해 부분 환불 반올림 문제를 피한다.
6. 주문 스냅샷의 상품명·가격·주소와 현재 마스터 값은 달라도 정상이다. 환불 후에도 최초 주문금액을 변경하지 않는다.
7. 결제 시도는 복수 가능, 성공은 최대 한 건. 성공액은 주문금액과 같다. paid/processing/completed 주문은 성공 결제가 필요하다.
8. pending_payment는 결제 성공·출고가 없다. 현재 버전에는 결제 대기 자동 만료 정책이 없으므로 경과 일수만으로 오류 판정하지 않는다.
9. 출고는 성공 결제 이후다. 출고 준비는 운송장·택배사·출고/배송 시각이 null일 수 있다. 완료 배송은 출고 시각≤완료 시각이다.
10. 출고 상세의 주문은 출고 묶음의 주문과 일치한다. 취소되지 않은 출고 배정 수량 합계≤주문 수량. completed 주문은 전량 배송 완료다.
11. 반품은 배송 완료 이후. 반품 접수와 대상 출고의 주문이 일치한다. 거절·취소를 제외한 반품 누적 수량≤출고 수량.
12. return_status의 received/closed는 received_at 필수. closed/rejected/cancelled는 closed_at 필수. rejected/cancelled는 입고 전 종료로 단순화했다.
13. 반품 환불은 입고 이후 요청하며 원결제와 같은 주문이다. 금액은 반품 수량×주문 당시 할인 후 단가다. 초기 정책에서는 반품 배송비·최초 배송비 환급을 제외한다.
14. 출고 전 전체 취소 환불은 return_id=null, 원 주문금액 전액이다. 미결제 취소는 환불 행이 없다.
15. 실패 환불은 누적 환불액에 포함하지 않는다. 성공 환불 합계≤원결제액. closed 반품은 해당 승인 반품금액만큼 환불 완료다.
16. 성공 결제·환불에만 완료 시각, 실패 시도에만 failure_code가 있다. 결제는 환불 후에도 원결제 성공 상태를 보존한다.
17. 상품·회원의 현재 비활성 상태는 과거 거래를 무효화하지 않는다. 재고·상품 상태 이력이 없어 과거 판매 가능성을 현재 상태만으로 판정하지 않는다.

## 검증과 한계

`scripts/validate.py`는 내보낸 CSV를 다시 읽어 생성기와 별개로 검사한다. 검증기 변이 테스트는 고의로 잘못된 금액·수량·외래키·전화·시간·카테고리 관계를 넣어 탐지 여부를 확인한다.

데이터는 재현 가능한 기능 검증용이다. 주문량·반품률·가격분포·상태 비중은 시장 대표성이 없다. 모든 이름·주소·이메일은 가상이며, 전화번호가 실제 미사용 번호임을 보증하지 않는다. 연락·배송에 사용하지 않는다.

## 후속 오염 데이터 설계

| 유형 | 예 | 기대 동작 |
|---|---|---|
| 표기 차이 | 전화 공백/하이픈, 금액 쉼표/원 | 승인된 규칙으로 표준화 |
| 의미 확실한 결측 | phone의 빈칸/없음 | 규칙에 따라 null, 원문 보존 |
| 의미 불확실 | 수량 0, 미정, 모호한 날짜 | 근거와 함께 검토 요청 |
| 구조 오류 | 중복 PK, 존재하지 않는 SKU | 진단·보류; 추측 연결 금지 |
| 계산 모순 | 합계 불일치 | 진단; 어떤 값이 원인인지 모르면 자동 수정 금지 |
| 정상 예외 | 대량 주문, 배송 전 빈 운송장 | 수정하지 않음 |
| 정보 손실 | 잘린 전화번호, 삭제 행 | 탐지 가능한 범위만 표시; 원값 복원 요구 금지 |

담당자 A/B/C/D별 표기 습관과 신규 담당자 패턴을 분리한다. 개발·평가 파일과 정답은 별도 디렉터리로 두고 평가 정답을 서비스 입력에 섞지 않는다. 비율·seed·변형 규칙은 오염 생성기에 명시한다.
